# Ray Poker — 产品需求文档（PRD）

| 项目 | 说明 |
|------|------|
| 产品名称 | Ray Poker |
| 形态 | H5 移动端德州扑克（实时多人） |
| 文档版本 | v0.1 |
| 状态 | 草案，随开发迭代更新 |

---

## 1. 背景与目标

### 1.1 背景

在移动端浏览器中提供可快速开局、低摩擦的德州扑克体验，支持实时同步牌桌状态，为后续好友房、匹配、赛事等扩展预留架构空间。

### 1.2 产品目标

- **G1**：玩家可在手机浏览器完成注册/进房、上桌、完整打完一手牌并看到结算结果。  
- **G2**：牌局状态通过服务端权威计算，客户端负责展示与输入，降低作弊与分歧。  
- **G3**：核心牌局逻辑（`PokerEngine`）与网络层解耦，便于单测与规则迭代。

### 1.3 目标用户

- 休闲玩家：碎片时间娱乐，重视加载速度与操作顺手。  
- 熟人局组织者：需要稳定房间与清晰结算。

---

## 2. 范围与非目标

### 2.1 本期范围（MVP 导向）

- 房间/牌桌基础模型（人数、盲注、按钮位）。  
- 一手牌完整流程：发底牌 → 翻前/翻牌/转牌/河牌 → 摊牌或死摊 → 分池结算。  
- 实时通信：Socket 推送公共状态；行动请求与校验。  
- H5 端牌桌 UI：公共牌、底池、行动区（跟注/加注/弃牌等）。

### 2.2 非目标（本期不做或延后）

- 真钱支付、法币出入金、博彩牌照相关能力。  
- 复杂反作弊（设备指纹、行为风控）深度方案。  
- 原生 App 上架与推送（可以 Web 为主，后续再评估壳包）。

## 3. 德州扑克规则与引擎约定

本节为**服务端引擎与产品表现**的共同约定；与现场「House Rule」冲突时，以本文档为准。

### 3.1 基础规则

- 游戏类型：**无限注德州扑克（No-Limit Texas Hold'em）**。  
- 单桌人数：建议 **2–9** 人（具体上下限可在房间配置中定义）。  
- 使用标准 **52 张牌**，无鬼牌。  
- 每名玩家 **2 张底牌**，公共牌最多 **5 张**（Flop 3 + Turn 1 + River 1）。  
- **按钮（D 位）**决定发牌顺序与盲注位置；每手结束后按钮按顺时针移动。

### 3.2 奇数筹码分配（Odd Chip）

当某一奖池需在多名玩家之间平分且出现**无法整除的余数（奇数筹码）**时：

- 将余数筹码按**顺时针方向**，从**庄家按钮（D 位）**的下一位开始，依次每人最多多分配 **1** 个大盲注单位（或当前房间约定的最小拆分单位），直到分完。  
- 若仍存在规则边界情况（例如全下层级与边池交错），在实现 `distributePot` 时**以本节优先级高于默认「随机」**；具体实现须与测试用例对齐并记录在变更日志中。

### 3.3 行动顺序与轮次结束

- 每一街（street）从需行动玩家的顺序依规则推进。  
- 当所有未弃牌玩家在本街**下注额对齐**且无人待决行动时，进入下一街或进入摊牌。  
- **Check** 仅当当前最高下注等于该玩家本街已投入时允许；否则须 **Call / Fold / Raise（含 All-in）** 等合法行动。

### 3.4 All-in 与边池概念

- 玩家筹码不足以跟注时，可形成 **All-in**；该玩家本街不再追加下注，但仍可参与**其有权竞争的奖池**的分配。  
- 多名玩家以不同额度全下时，形成 **主池 + 多个边池（Side Pots）**；每个池的参与者集合由「有效投入额度」决定。

### 3.5 摊牌与死摊

- **摊牌（Showdown）**：在河牌圈结束后，未弃牌玩家以最佳 5 张组合比牌。  
- **死摊**：当仅剩一名未弃牌玩家时，无需摊牌即可赢得所有其有资格的池。

### 3.6 边池计算：升序切分法

引擎在计算边池时采用 **「升序切分法」**（按玩家**有效投入**从低到高排序后逐层切分）：

1. 收集本手已投入或 All-in 的各玩家在本手的**层级贡献**（以实现中数据结构为准）。  
2. 将贡献额度**升序**排列，在每一档位切出一层池：该层金额 × 有资格玩家数，计入对应 **Pot**，并更新剩余待切分贡献。  
3. 生成 **主池（level 0）** 与 **边池（level 1…n）**，每一池维护 `amount` 与 **`eligiblePlayers`（有资格分池的玩家 ID）**。  
4. 切分结果与前端展示的「主池/边池」文案一致，且在单测中用固定场景锁定。

### 3.7 牌力比较

- 标准成牌等级：高牌 → 一对 → 两对 → 三条 → 顺子 → 同花 → 葫芦 → 四条 → 同花顺。  
- 同等级比较踢脚（kickers）；具体比较序列由 `PokerEngine` 实现与单元测试共同保证。

### 3.8 最后一手与收尾阶段（FINAL_HAND）

当房间或牌局进入**解散、维护结束本桌、或规则要求的最后一手**时：

- 进入 **`FINAL_HAND` 阶段**：完成当前已在进行的一手牌的全部结算（含摊牌、分池、奇数筹码分配）。  
- 在该阶段**禁止新开下一手**或仅允许只读展示（由产品开关决定）；引擎在状态机中明确与 `SHOWDOWN` 的先后关系，避免重复结算。  
- 收尾完成后转入房间结束态或等待房主操作（具体由房间状态机定义）。

## 4. 功能需求概要

### 4.1 用户与身份

- 匿名或账号登录（实现阶段选型）。  
- **昵称**、**头像**（可选）在牌桌展示。

### 4.2 房间与牌桌

- 创建房间：盲注级别、最大人数、是否允许旁观等。  
- 加入房间：通过房间号/链接进入。  
- 入座/离座、**暂离（起立）** 与 `PlayerStatus` 对齐。

### 4.3 实时同步

- 客户端通过 **Socket** 接收：阶段、公共牌、池、当前行动位、合法行动范围等。  
- 客户端发送：行动意图（由服务端校验后生效）。

### 4.4 H5 体验

- 视口适配移动端；禁止缩放以保证布局稳定（见前端 `viewport` 配置）。  
- 主要操作区适合单手触达；弱网提示与断线重连（后续迭代细化）。

## 6. 非功能需求

- **正确性**：引擎行为可单测覆盖；关键规则（边池、奇数筹码、状态机）需回归用例。  
- **延迟**：行动提交到多数玩家看到状态更新的 P95 目标在实现阶段根据部署环境再定。  
- **安全**：服务端校验所有行动；不信任客户端传来的筹码与牌面。
